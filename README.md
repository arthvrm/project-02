# Класифікація внутрішніх запитів

CLI pipeline читає запити з CSV, класифікує кожен запит через Google Gemini, перевіряє відповідь Pydantic-моделлю та записує JSON-результат і Markdown-звіт.

## Запуск

### Вимоги

- Python 3.12+
- API-ключ Google Gemini
- `uv` (рекомендовано) або `pip`

Встановлення залежностей через `uv`:

```bash
uv sync
```

Альтернативно, у віртуальному середовищі:

```bash
python -m venv .venv
# Windows PowerShell
.venv\Scripts\Activate.ps1
або
.venv/Scripts/activate
python -m pip install -r requirements.txt
```

### Змінні середовища

Створіть файл `.env` у корені проєкту(приклад можна зкопіюапти з .env.example):

```env
GEMINI_API_KEY=ваш апі ключ
LLM_MODEL=gemini-3.5-flash-lite
MAX_RETRIES=3
INPUT_FILE=inputs/input_requests.csv
OUTPUT_FILE=results/output.json
REPORT_FILE=results/report.md
```

Обов'язкова змінна лише `GEMINI_API_KEY`. Інші мають значення за замовчуванням:


### Команда запуску

після активації `.venv`:

```bash
python -m app.main
```

Вхідний файл має містити колонки `id`, `channel`, `timestamp`, `raw_text`. Приклад уже є в `inputs/input_requests.csv`. Після запуску створюються `results/output.json` і `results/report.md`.

Тести:

```bash
uv run pytest
```

## Де рішення ламається та обмеження

### Невалідний вивід LLM

Відповідь очікується як чистий JSON із точно визначеними полями. Pydantic перевіряє enum-значення, типи, обов'язкові поля та забороняє зайві поля. Якщо LLM повертає Markdown, пошкоджений JSON або неправильну схему, pipeline повторює виклик до `MAX_RETRIES` разів. Якщо всі спроби невдалі, запит не потрапляє до `output.json`, але потрапляє до секції `Failed Requests` у звіті.

Це закриває помилкове прийняття структури, але не гарантує семантичну правильність класифікації. Автоматичної перевірки якості, fallback-моделі чи ручної черги на повторну обробку немає.

### Великий обсяг даних

CSV читається повністю в пам'ять, а запити обробляються послідовно. Для великого файлу це збільшує час виконання, використання пам'яті та кількість API-викликів. Один тимчасовий збій також не зупиняє весь pipeline для інших рядків, але результат зберігається лише після завершення всієї обробки: аварія посередині може втратити вже отримані класифікації.

Наразі немає batch-викликів, паралелізму, rate limiting, checkpointing або відновлення після переривання.

### Недетермінізм

Однаковий запит може отримати різні категорію, пріоритет або список дій через стохастичність LLM. У коді не фіксується seed/temperature і немає версіонування промпта чи моделі. Pydantic гарантує формат, але не повторюваність і не правильність змісту.

### Вартість токенів

Кожен запит містить довгий інструктивний prompt, а невдала валідація може спричинити до `MAX_RETRIES` оплачуваних викликів. Вартість не оцінюється і не обмежується в коді; немає ліміту токенів, кешу, підрахунку usage або budget guard. Фактична ціна залежить від обраної Gemini-моделі та довжини CSV-запитів.

### Інші операційні обмеження

Помилка читання CSV або некоректний рядок `InputRequest` завершує програму до формування результатів. API-ключ не перевіряється окремим зрозумілим повідомленням на старті. Dockerfile зараз посилається на `requirements.txt`, якого немає в репозиторії, тому Docker-запуск потребує окремого виправлення.

## Що покращити за більше часу

1. Узгодити провайдер і конфігурацію: або повністю перейти на Gemini з валідним дефолтним `LLM_MODEL`, або реалізувати явний Ollama-режим.
2. Використати structured output/function calling, щоб зменшити кількість невалідних відповідей, і додати тестові fixtures для відповідей LLM.
3. Додати checkpointing та ідемпотентне збереження після кожного запиту, щоб безпечно відновлювати перервані запуски.
4. Обробляти CSV потоково, додати контрольовану паралельність, rate limiting та exponential backoff для API.
5. Додати ліміти бюджету й токенів, usage-метрики, кешування однакових запитів і прогноз вартості до запуску.
6. Зафіксувати параметри генерації, версію промпта та модель; додати evaluation-набір, метрики якості й regression-тести.
7. Покращити observability: окремі причини помилок, correlation IDs, безпечне логування та зрозумілу перевірку конфігурації.
8. Виправити Dockerfile під `pyproject.toml`/`uv` і додати CI з тестами та перевіркою формату вхідних даних.
