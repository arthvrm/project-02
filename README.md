# Класифікація внутрішніх запитів

CLI pipeline читає запити з CSV, класифікує кожен запит через Google Gemini, перевіряє відповідь Pydantic-моделлю та записує JSON-результат і Markdown-звіт.

## Запуск

### Вимоги

- Python 3.12+
- API-ключ Google Gemini
- `uv` (рекомендовано) або `pip`

Встановлення залежностей через `uv`:

```bash
uv sync
```

Альтернативно, у віртуальному середовищі:

```bash
python -m venv .venv
# Windows PowerShell
.venv\Scripts\Activate.ps1
або
.venv/Scripts/activate
python -m pip install -r requirements.txt
```

### Змінні середовища

Створіть файл `.env` у корені проєкту(приклад можна зкопіюапти з .env.example):

```env
GEMINI_API_KEY=ваш апі ключ
LLM_MODEL=gemini-3.5-flash-lite
MAX_RETRIES=3
INPUT_FILE=inputs/input_requests.csv
OUTPUT_FILE=results/output.json
REPORT_FILE=results/report.md
```

### Команда запуску

після активації `.venv`:

```bash
python -m app.main
```

Вхідний файл має містити колонки `id`, `channel`, `timestamp`, `raw_text`. Приклад уже є в `inputs/input_requests.csv`. Після запуску створюються `results/output.json` і `results/report.md`.

Тести:

```bash
uv run pytest
```

## Де рішення ламається та обмеження

### Невалідний вивід LLM

Відповідь LLM має відповідати заданій Pydantic-моделі. Вона перевіряє типи, допустимі значення, обов'язкові поля та забороняє зайві поля.

Якщо LLM повертає невалідний JSON або неправильну структуру, pipeline повторює запит до `MAX_RETRIES` разів. Якщо всі спроби невдалі, запит записується у `Failed Requests` у звіті та не потрапляє до `output.json`.

Це захищає від помилок у форматі, але не перевіряє правильність самої класифікації. Зараз також немає fallback-моделі або ручної повторної обробки.

### Великий обсяг даних

CSV зараз повністю завантажується в пам'ять, а запити обробляються послідовно. Для великих файлів це збільшує використання пам'яті та час виконання.

Результати зберігаються після завершення всієї обробки, тому аварія під час виконання може призвести до втрати вже отриманих класифікацій.

Зараз немає batch-обробки, паралельності, rate limiting або checkpointing.

### Недетермінізм

LLM може по-різному класифікувати однаковий запит. Pydantic гарантує правильний формат відповіді, але не гарантує правильність її змісту.

Також зараз немає версіонування промпта та системи для автоматичної перевірки якості класифікацій.

### Вартість API-викликів

Кожен запит потребує окремого виклику LLM. Якщо відповідь не пройшла валідацію, retry збільшує кількість викликів.

Зараз pipeline не рахує використані токени, не оцінює вартість і не має budget limit або кешування однакових запитів.

### Інші операційні обмеження

Помилка читання CSV або невалідний вхідний рядок може зупинити pipeline до формування результатів.

Перевірка конфігурації та API-ключа зараз мінімальна.

Docker-запуск також потребує узгодження Dockerfile з актуальною структурою проєкту та `requirements.txt`.

## Що покращити за більше часу

1. Додати structured output для прямого отримання `RequestClassification` від LLM.
2. Додати checkpointing та збереження результату після кожного успішного запиту.
3. Обробляти CSV потоково та додати контрольовану паралельність і rate limiting.
4. Додати exponential backoff для тимчасових помилок API.
5. Додати підрахунок токенів, оцінку вартості та budget limit.
6. Додати кешування однакових запитів.
7. Створити evaluation-набір для перевірки якості класифікації та regression-тестів.
8. Додати версіонування промпта і моделі.
9. Покращити logging та обробку окремих типів помилок.
10. Додати CI з автоматичним запуском тестів і перевіркою вхідних даних.
